# Docker: практический курс для Linux/DevOps

Подготовлено 9 ноября 2026 года. Формат: 8 недель, 24 занятия по 2–3 часа, около 60 часов. Примерно треть времени — чтение и разбор, остальное — практика.

Курс рассчитан на человека, который уже работает с Linux и запускал сервисы через Docker Compose, но хочет системно понимать сборку, изоляцию, сети, данные и эксплуатацию. Знание Linux позволяет быстрее пройти вводную часть, но практические проверки пропускать не стоит.

## 1. Результат

После курса ты сможешь самостоятельно:

- Объяснить связь процесса, контейнера, образа, registry и Docker Engine.
- Собрать образ приложения и объяснить его слои, кэш и зависимости.
- Развернуть несколько сервисов через Compose.
- Найти причины сетевых ошибок, циклических перезапусков и проблем с правами.
- Сохранить данные, восстановить их на другом стенде и проверить результат.
- Ограничить права и ресурсы контейнера.
- Построить цикл сборки, проверки, публикации и отката приложения.
- Описать ограничения одного Docker-хоста и границу между Compose и оркестратором.

Итоговый проект — небольшой сервис учёта инфраструктуры: nginx → API → PostgreSQL. API хранит записи о тестовых серверах: имя, адрес, роль и комментарий. Можно написать его на знакомом Python или Go. Разработка интерфейса не требуется: достаточно HTTP API и curl.

### Как обращаться со старыми примерами

| В книге встретилось | Как работать в курсе |
| --- | --- |
| `docker-compose` | Использовать современную команду `docker compose` |
| Верхнеуровневое `version: "2"` или `"3"` | Писать `compose.yaml` по Compose Specification, без этого поля |
| `--link`, ручное закрепление IP | Для стенда использовать пользовательскую сеть и DNS-имена сервисов |
| Docker Machine, boot2docker | Не использовать в основном стенде с Linux Engine |
| Создание релизов через `docker commit` | Выполнять сборку из Dockerfile; commit рассматривать только как отдельный эксперимент |
| Старые storage driver и инструкции настройки cgroups | Сначала проверить фактическую конфигурацию через `docker info` |
| Отключение защиты ради запуска | Искать конкретную причину отказа и минимально нужное изменение |

Современный Compose использует Compose Specification. Номер версии CLI не равен старому номеру формата YAML. Проверяй `docker compose version`, а не пытайся определить возможности по полю `version`.

## 3. Стенд и порядок занятий

Рекомендуемый учебный стенд — отдельная Debian VM в Proxmox: 2 vCPU, 4 ГБ RAM, 30 ГБ диска. Это ориентир для небольшого проекта, а не требование Docker. Для переноса и восстановления понадобится вторая чистая VM или возможность создать её к концу курса.

Не использовать рабочие тома Nextcloud, Pi-hole и других домашних сервисов. Установку Docker Engine для выбранной ОС выполнять по [официальной инструкции](https://docs.docker.com/engine/install/). На Arch установку согласовать с документацией дистрибутива. Команды курса предполагают работающий Engine и доступ текущего пользователя к нему; при выбранной модели доступа может требоваться `sudo`.

Членство в группе `docker` на хосте с rootful Engine даёт полномочия уровня root. Не добавлять пользователей в эту группу автоматически ради удобства. Rootless изучается отдельно в занятии 17.

Проверка перед началом:

```bash
docker version
docker info
docker compose version
docker buildx version
curl --version
git --version
```

Выпиши версии клиента, сервера, Compose, архитектуру, cgroup driver, cgroup version и способ хранения образов из доступного вывода. При использовании удалённого Engine отдельно запиши `docker context show`: команды могут воздействовать на другой хост.

Для проекта создать Git-репозиторий с каталогами `app`, `nginx`, `labs`, `runbooks` и `backups`. Каталог backups не коммитить. В `.gitignore` также добавить `.env`, файлы секретов и временные данные. Сохранять только `.env.example` без настоящих паролей.

### Ритм одного занятия

1. 20–30 минут: чтение указанной темы.
2. 15–20 минут: объяснение своими словами и схема при необходимости.
3. 60–90 минут: лабораторная работа.
4. 15–20 минут: контрольные вопросы и запись результата.

Для каждого занятия сохранять `labs/NN.md`: цель, версии, команды, ожидаемый результат, фактический результат, объяснение ошибки и способ исправления. Перед сохранением вывода удалять секреты. `docker inspect` и `docker compose config` могут содержать конфиденциальные значения.

Переходить дальше, когда выполнен критерий приёмки. Успешный запуск без объяснения причины не считается завершением.

## 5. Занятия

### 1. Что представляет собой контейнер

**Читать:** U, главы 1–2; A — введение и изоляция.

**Разобрать:** образ как шаблон файловой системы и метаданных; контейнер как экземпляр со своим состоянием; registry как хранилище образов. Контейнер в Linux использует ядро хоста. Его изоляцию нельзя приравнивать к отдельной виртуальной машине.

**Практика:** выполнить лабораторную из раздела 6. Нарисовать связь CLI → Engine → контейнер и отдельно показать загрузку образа из registry.

**Приёмка:** объяснить, что будет после остановки и после удаления контейнера. Показать различие между образом и запущенным процессом.

**Вопросы:** почему образ Debian может работать на хосте с другим дистрибутивом? Почему Linux-контейнер не приносит собственное Linux-ядро?

### 2. Engine, процессы и изоляция

**Читать:** U, главы 2 и 6; A — namespaces и ограничения ресурсов; D — Engine security.

**Практика:** запустить долговременный процесс. Сравнить `docker top` с `ps` на VM. Найти PID процесса контейнера через `docker inspect`. На хосте сравнить `/proc/PID/ns` с namespace текущей оболочки. Сопоставить UID процесса в контейнере и на хосте с учётом режима Engine.

**Приёмка:** показать, какие процессы и namespace исследованы. Объяснить роли CLI, dockerd, containerd и runtime на уровне назначения, без заучивания внутренних вызовов.

**Вопросы:** за что отвечают namespaces, а за что cgroups? Почему root внутри контейнера требует внимания к модели запуска и подключённым ресурсам?

### 3. Жизненный цикл, PID 1 и сигналы

**Читать:** U, главы 5–6; A — запуск и остановка контейнеров.

**Практика:** сравнить `run`, `create`, `start`, `stop`, `kill`, `rm`, `exec` и `attach`. В отдельном контейнере запустить процесс, завершающийся с ненулевым кодом. Проверить `ps -a`, `logs` и `.State` через inspect. Сравнить exec- и shell-формы запуска в небольшом образе.

**Приёмка:** определить exit code и основной процесс. Показать корректную остановку приложения по SIGTERM. Не считать каждый код 137 доказательством OOM: проверить контекст.

**Вопросы:** почему выход главного процесса завершает контейнер? Чем новый процесс через exec отличается от подключения к потокам главного процесса?

### 4. Dockerfile и первый образ

**Читать:** U, глава 4; A — создание образов; D — Dockerfile reference.

**Практика:** подготовить API с `/health` и `/version`, пока без БД. В Dockerfile использовать `FROM`, `WORKDIR`, `COPY`, `RUN`, `USER`, `CMD`. Добавить `.dockerignore`. Собрать `infra-api:lesson04`. API слушает `0.0.0.0` внутри контейнера; порт хоста публикуется только на loopback.

**Приёмка:** образ собирается из сохранённых исходников. API отвечает через curl. В контейнере подтверждён непривилегированный UID. Объяснить назначение каждой инструкции.

**Вопросы:** что относится ко времени сборки, а что ко времени запуска? Почему `EXPOSE` сам по себе не публикует порт хоста?

### 5. Слои, контекст и кэш

**Читать:** U, глава 4; D — Building best practices.

**Практика:** собрать образ дважды с подробным выводом BuildKit. Затем отдельно изменить код, зависимости и файл вне контекста сборки. Зафиксировать, какие шаги использовали кэш. Проверить `docker history` и размер образа. Удалить ненужные файлы из контекста через `.dockerignore`.

**Приёмка:** изменение кода не запускает повторную установку неизменившихся зависимостей при корректном порядке инструкций. Есть объяснение наблюдений, а не только сравнение секунд.

**Вопросы:** чем `--pull` отличается от `--no-cache`? Почему удаление файла в следующем слое не гарантирует его удаления из предыдущего слоя?

### 6. Multi-stage и содержимое релиза

**Читать:** U — работа с образами; D — multi-stage builds и build secrets.

**Практика:** сделать стадии сборки и запуска. Для Go — вынести компиляцию в builder. Для Python — подготовить wheels или отдельную стадию установки совместимых зависимостей. Сравнить итоговый состав и запуск. Добавить `.gitignore` и проверить, что `.env` и ключи исключены из build context.

**Приёмка:** финальный образ не содержит ненужной цепочки сборки. Обе HTTP-проверки проходят. Записаны размер, UID и состав необходимых runtime-зависимостей.

**Вопросы:** почему меньший размер сам по себе не доказывает безопасность? Почему секрет нельзя безопасно передавать через обычный `ARG` или `ENV` сборки?

### 7. Writable layer, bind mount, volume и tmpfs

**Читать:** U, глава 5, Storage Volumes; A — хранение данных; D — Volumes.

**Практика:** создать тестовый файл в writable layer, bind mount и именованном volume. Остановить, запустить и пересоздать контейнеры. Затем подключить конфигурацию read-only. Отдельно проверить временные данные в tmpfs.

**Приёмка:** таблица наблюдений для каждого способа хранения. Показать, где сохранился файл после пересоздания и почему.

**Вопросы:** почему перезапуск контейнера не равен его пересозданию? Как mount может скрыть файлы, уже присутствующие в образе? Чем `docker export` отличается от полноценной резервной копии приложения?

### 8. PostgreSQL и резервная копия

**Читать:** U — внешнее состояние; A — persistent storage; D — Volumes и документация выбранного образа PostgreSQL.

**Практика:** выбрать поддерживаемую major-версию PostgreSQL и записать её. Проверить путь хранения в документации именно этой версии образа. Создать именованный volume, таблицу и 10 тестовых записей. Пересоздать только контейнер и проверить записи. Выполнить логический дамп через `pg_dump`; восстановить его в отдельную чистую БД совместимой версии.

**Приёмка:** восстановленные строки совпадают с исходными. Пароль не сохранён в Git. Записаны команда, код завершения, размер дампа и результат SQL-проверки.

**Вопросы:** почему копирование работающего каталога PostgreSQL обычным tar не заменяет согласованный бэкап? Почему изменение переменной инициализации не обязательно меняет уже созданную БД?

### 9. Bridge, DNS и опубликованные порты

**Читать:** U — Container Networking; A — сети; D — Networking и Packet filtering and firewalls.

**Практика:** соединить два контейнера пользовательской bridge-сетью. Выполнить запрос по имени контейнера. Проверить ошибку при отсутствии общей сети. Опубликовать HTTP-порт на `127.0.0.1`. Проверить доступ с VM и отдельно с другого хоста. БД не публиковать.

**Приёмка:** таблица «источник → имя/IP → порт → результат». Объяснить каждый результат через DNS, адрес прослушивания, публикацию или фильтрацию.

**Вопросы:** что означает localhost внутри контейнера? Почему `INPUT DROP` на хосте сам по себе не доказывает недоступность опубликованного контейнерного порта? Правила Docker не отключать ради эксперимента.

### 10. Compose как описание проекта

**Читать:** U, глава 7 — процессы развёртывания; D — Compose Specification. Синтаксис Compose брать из D.

**Практика:** перенести nginx, API и БД в `compose.yaml`. Настроить имена сервисов, volumes и сети. Выполнить `docker compose config --quiet`, затем `up -d`, `ps`, `logs`, `exec`. Запустить второй экземпляр через другое имя проекта и другой порт.

**Приёмка:** оба экземпляра имеют отдельные данные и не конфликтуют по именам и портам. Их можно обслуживать независимо.

**Вопросы:** чем `image` отличается от `build`? Как имя проекта влияет на имена ресурсов? Почему жёсткий `container_name` часто мешает повторному развёртыванию?

### 11. Конфигурация, готовность и повторные подключения

**Читать:** D — переменные Compose, secrets и startup order; U — внешняя конфигурация.

**Практика:** добавить `/ready`, который проверяет соединение API с БД. Настроить healthcheck PostgreSQL и `depends_on` с `service_healthy`. Искусственно задержать готовность БД. Проверить восстановление API после потери соединения с БД; предусмотреть retry с задержкой.

**Приёмка:** различаются состояния «процесс работает», «проверка здоровья проходит» и «приложение обслуживает запросы». API переживает временную потерю БД без ручного исправления адресов.

**Вопросы:** почему обычный `depends_on` не гарантирует готовность? Почему Docker restart policy не перезапускает контейнер только из-за статуса unhealthy? `.env` не считать хранилищем секретов; локальные Compose secrets не приравнивать к зашифрованному vault.

### 12. Сборка единого стека

**Читать:** U, глава 7; P — подходы к доставке приложений.

**Практика:** реализовать создание и чтение записей о серверах. Настроить nginx как reverse proxy. Ввести front-сеть для nginx/API и back-сеть для API/БД. Опубликовать только nginx. Привести конфигурацию к одному документированному способу запуска.

**Приёмка:** curl через nginx создаёт и читает запись. У PostgreSQL нет опубликованного порта хоста. После пересоздания API запись сохраняется. Изоляция сетей подтверждена проверкой фактических подключений.

**Вопросы:** какие адреса использует браузер или curl снаружи, nginx внутри и API при соединении с БД? Какие данные должны пережить замену каждого сервиса?

### 13. Диагностика процесса и приложения

**Читать:** U, главы 6 и 8; P — практические приёмы исследования.

**Практика:** последовательно создать три неисправности: неверная команда запуска, отсутствующая обязательная переменная и неправильный путь к конфигурации. Для каждой использовать `ps -a`, `logs`, `inspect`, а при необходимости — `events` с ограниченным интервалом.

**Приёмка:** три кратких отчёта «симптом → гипотеза → проверка → причина → исправление → повторная проверка». Пересборку выполнять только при изменении образа, а не как универсальное средство.

**Вопросы:** почему отсутствие ошибок в логах не доказывает доступность сервиса? Что делать, если в минимальном образе отсутствует shell?

### 14. Диагностика сети по слоям

**Читать:** U, глава 8; D — bridge networking и port publishing.

**Практика:** сломать по одному: имя БД, общую сеть, порт назначения, адрес прослушивания API, upstream nginx. Различать ошибку разрешения имени, connection refused, timeout и HTTP 502. Проверять соединения из нужной точки сети; диагностический контейнер подключать только к нужной учебной сети.

**Приёмка:** пять сбоев объяснены по данным проверок. В отчёте указано, откуда выполнялся запрос. Для каждого исправления повторён исходный запрос.

**Вопросы:** почему успешный curl с хоста не доказывает доступность из nginx? Почему замена DNS-имени на текущий IP контейнера обычно скрывает причину и создаёт новую проблему?

### 15. Права, место на диске и логи

**Читать:** U, главы 5–6 и 8; D — logging и troubleshooting.

**Практика:** создать отказ записи из-за UID/GID в отдельном каталоге. Проверить права без `chmod 777`. Изучить `docker system df -v`, объём логов и свободное место VM. Настроить ограничение логов выбранного logging driver и пересоздать учебный сервис, если это требуется для применения.

**Приёмка:** причина отказа записи доказана. Рост логов ограничен. Есть инструкция освобождения места с предварительной проверкой объектов, которые будут удалены.

**Вопросы:** почему `docker system prune` не является исправлением приложения? Почему `down -v`, `volume rm` и очистка с volumes требуют проверки данных? Диск до полного заполнения намеренно не доводить.

### 16. CPU, память, PID и завершение процессов

**Читать:** U — Resource Quotas; A — ограничения ресурсов; D — Resource constraints.

**Практика:** на небольшой нагрузке проверить ограничения CPU и памяти. Отдельно создать контролируемое превышение лимита памяти внутри ограниченного контейнера. Проверить `docker stats`, inspect и доступные события/журналы. Установить небольшой, достаточный для приложения лимит процессов и проверить его конфигурацию без fork bomb.

**Приёмка:** заданные ограничения видны в конфигурации; наблюдения записаны. OOM отличается от обычного завершения и принудительного SIGKILL по совокупности признаков.

**Вопросы:** почему лимит CPU не равен резервированию выделенного ядра? Почему контейнер без лимитов может создать проблемы соседним сервисам?

### 17. Полномочия контейнера и rootless

**Читать:** A — изоляция; D — Engine security и Rootless mode.

**Практика:** для API проверить запуск от non-root, `read_only`, `tmpfs` для временных файлов, `cap_drop: [ALL]`, `no-new-privileges`. Применять ограничения по одному и фиксировать необходимые пути записи. На отдельном тестовом окружении сравнить rootless и rootful Engine по доступу к daemon, сети и хранению данных.

**Приёмка:** API работает с выбранными ограничениями. У каждого исключения есть причина. Объяснена разница между non-root процессом контейнера и rootless daemon.

**Вопросы:** почему нельзя бездумно подключать Docker socket к приложению? Почему read-only mount сокета не превращает API Docker в API только для чтения? Почему `privileged` не является штатным способом исправить права?

### 18. Образы, секреты и защитные профили

**Читать:** D — build secrets, Dockerfile USER, security и документация выбранного сканера.

**Практика:** проверить происхождение базового образа. Зафиксировать digest релизного образа. Просканировать его доступным инструментом, например Trivy или Docker Scout, если он доступен в твоём окружении. Разобрать три находки: пакет, затронутая версия, исправление и применимость. Проверить SecurityOpt и состояние AppArmor на Linux-хосте, где он включён.

**Приёмка:** есть краткий отчёт о рисках и способе обновления. Секреты отсутствуют в Dockerfile, исходниках, истории сборки и опубликованных материалах. Для учебной проверки использовать фиктивные секреты.

**Вопросы:** почему успешный скан не гарантирует отсутствие уязвимостей? Почему фиксированный digest требует отдельного процесса обновления? AppArmor и seccomp глобально не отключать ради запуска стенда.

### 19. Registry и идентичность релиза

**Читать:** U, глава 4 — registries; P — доставка; D — image push/pull.

**Практика:** выбрать доступный registry. Собрать образ из конкретного Git commit. Присвоить тег с commit SHA, опубликовать и записать digest. На втором стенде скачать тот же образ и проверить `/version`. Учётные данные registry хранить вне Git и вывода отчётов.

**Приёмка:** связаны Git commit, тег, digest и версия запущенного API. На целевой VM не требуется собирать релиз заново.

**Вопросы:** почему тег можно переназначить? Почему одного `latest` недостаточно для точного отката? Чем digest опубликованного образа отличается от имени локального тега?

### 20. Сборка и проверки в CI

**Читать:** U — testing и delivery; P — CI-подходы; D — Build best practices.

**Практика:** выбрать GitLab CI или GitHub Actions. Добавить проверку приложения, валидацию Compose, сборку и smoke test образа. После успешных проверок публиковать релизный образ. Для учебного runner не использовать рабочий сервер; отдельно описать полномочия выбранного способа доступа к Engine.

**Приёмка:** ошибочный код блокирует публикацию. Успешная сборка даёт образ с привязкой к commit. В логах CI нет секретов. Задание выполняется повторно из чистого checkout.

**Вопросы:** что именно проверяет smoke test? Почему доступ runner к Docker socket означает высокие полномочия? Как избежать пересборки другого артефакта между проверкой и доставкой?

### 21. Обновление, откат и восстановление

**Читать:** U — production и внешнее состояние; P — эксплуатационные подходы; D — Volumes.

**Практика:** создать релизы v1 и v2 без несовместимой миграции БД. Обновить API, проверить данные и вернуть прежний digest. Затем восстановить дамп занятия 8 в отдельный Compose-проект с новым volume. Измерить время восстановления и определить, до какого момента доступны данные.

**Приёмка:** продемонстрированы отдельно откат кода и восстановление данных. Восстановление не перезаписывает исходный стенд. В отчёте указаны фактические RTO/RPO учебного эксперимента.

**Вопросы:** почему возврат старого образа не отменяет миграцию схемы? Когда одного логического дампа недостаточно? Как проверить бэкап, кроме успешного завершения команды его создания?

### 22. Практический экзамен по сбоям

**Читать:** U, глава 8; свои отчёты занятий 13–18.

**Практика:** подготовить пять независимых сломанных конфигураций: неверный DNS, права на файл, ошибочная переменная, неготовая БД, неправильный upstream. По возможности попросить другого человека выбрать порядок; при самостоятельной работе выдержать паузу и не смотреть в исправления. На случай дать 15–20 минут.

**Приёмка:** найдены все пять причин. На каждый случай есть подтверждающая проверка и проверка восстановления. Переустановка Docker и отключение защит не считаются решением.

**Вопросы:** какие данные нужны до первого изменения? Как отличить первопричину от последующего симптома?

### 23. Перенос на чистую VM

**Читать:** U — delivery; свои runbooks.

**Практика:** развернуть проект на второй VM только по README, из registry и резервной копии. Не переносить каталог Docker Engine целиком. Проверить доступ, данные и конфигурацию. Перезагрузить только учебную VM и проверить возвращение сервисов.

**Приёмка:** стенд восстановлен без неописанных ручных шагов. Измерено время. Проверены работоспособность API, сохранность строк, логи и состояние контейнеров после reboot.

**Вопросы:** какие части восстанавливаются из Git, registry, секретов и бэкапа? Почему несколько контейнеров на одном хосте не дают отказоустойчивость к потере этого хоста?

### 24. Сдача проекта и проверка понимания

**Практика:** пройти итоговый чек-лист. За 10 минут объяснить путь запроса от curl до SQL, цикл релиза и порядок восстановления. Затем без подсказки диагностировать один ранее встречавшийся сбой.

**Приёмка:** все обязательные критерии раздела 8 выполнены. README позволяет повторить развёртывание. Выводы подтверждены сохранёнными проверками.

**После курса:** отдельным маршрутом изучить Swarm или Kubernetes, rolling updates, многосерверную сеть и распределённое хранение. Переходить к этому после уверенной эксплуатации текущего проекта.

## 6. Первая лабораторная: образ, контейнер и потеря writable layer

Выполнять на учебном Engine. Если имена уже заняты, выбрать другой префикс и заменить его во всех командах. Примеры используют учебные теги; перед выполнением проверить доступность образов. Для итогового проекта записывать точные версии и digest.

### Шаг 1. Запустить короткий процесс

```bash
docker run --name dc-lab01-short alpine:3.22 sh -c 'echo container-started; uname -r'
docker ps
docker ps -a --filter name=dc-lab01-short
docker logs dc-lab01-short
docker inspect --format '{{.State.Status}} {{.State.ExitCode}}' dc-lab01-short
```

Ожидается: контейнер завершён с кодом 0. В обычном `docker ps` его нет, в `docker ps -a` он присутствует. `uname -r` показывает ядро Linux-среды, на которой работает Engine.

### Шаг 2. Создать файл и перезапустить контейнер

```bash
docker run -d --name dc-lab01-state alpine:3.22 sleep 3600
docker exec dc-lab01-state sh -c 'echo lesson-01 > /tmp/proof.txt'
docker exec dc-lab01-state cat /tmp/proof.txt
docker stop dc-lab01-state
docker start dc-lab01-state
docker exec dc-lab01-state cat /tmp/proof.txt
docker diff dc-lab01-state
```

Ожидается: файл сохранился после stop/start. Это тот же контейнер с тем же writable layer.

### Шаг 3. Пересоздать контейнер

Следующие команды удаляют только учебный контейнер `dc-lab01-state` и его writable layer. Именованных volumes в этом примере нет.

```bash
docker stop dc-lab01-state
docker rm dc-lab01-state
docker run -d --name dc-lab01-state alpine:3.22 sleep 3600
docker exec dc-lab01-state sh -c 'test -e /tmp/proof.txt'
```

Ожидается: последняя команда завершится с кодом 1, потому что файла в новом контейнере нет. Проверить код сразу через `echo $?`. Это ожидаемая часть эксперимента.

### Шаг 4. Запустить HTTP-сервис

```bash
docker run -d --name dc-lab01-web -p 127.0.0.1:18080:80 nginx:stable-alpine
curl -I http://127.0.0.1:18080/
docker port dc-lab01-web
docker logs --tail 20 dc-lab01-web
docker inspect --format '{{.Config.Image}}' dc-lab01-web
```

Ожидается: ответ nginx и публикация на loopback учебного хоста. Если Engine удалённый, запрос к localhost нужно выполнять на его хосте или настроить SSH forwarding. Если порт занят, выбрать свободный и изменить обе команды.

### Шаг 5. Отчёт и очистка

Ответить письменно:

1. Почему короткий контейнер остановился, а образ остался?
2. Почему файл пережил stop/start, но не удаление контейнера?
3. Где находится порт 18080 и где порт 80?
4. Почему localhost ноутбука и localhost удалённого Engine могут быть разными адресатами?

Очистка удалит только три названных учебных контейнера:

```bash
docker stop dc-lab01-state dc-lab01-web
docker rm dc-lab01-short dc-lab01-state dc-lab01-web
```

Не использовать для этой лабораторной глобальные команды prune.

## 7. Самопроверка: ключевые ответы

Сначала сформулировать самостоятельно, затем свериться.

| Ситуация | Что нужно понимать |
| --- | --- |
| Контейнер завершился с кодом 0 | Главный процесс мог штатно закончить работу; контейнер не обязан быть долгоживущим |
| Контейнер запущен, но HTTP не отвечает | Проверить процесс, адрес прослушивания, порт, публикацию, сеть и фильтрацию |
| API обращается к БД через localhost | В обычной отдельной сети он обращается к самому себе; нужен адрес БД в общей сети |
| Файл исчез после пересоздания | Проверить, был ли он только в writable layer и какой volume подключён к новому контейнеру |
| Изменён `.env`, выполнен restart | Перезапуск существующего контейнера не заменяет его конфигурацию окружения; обычно нужно пересоздание через up |
| `depends_on` задан, БД ещё не готова | Порядок запуска и готовность — разные условия; нужны подходящая проверка и устойчивость клиента |
| Контейнер unhealthy | Это результат healthcheck; сам по себе он не означает автоматический restart Docker Engine |
| Exit code 137 | Процесс завершён SIGKILL; возможны разные причины, включая OOM и явное принудительное завершение |
| Тег образа совпадает | Под ним могут оказаться разные образы; проверить digest |
| Сделан откат API | Состояние и схема БД сами не откатываются |
| Дамп создан | Нужна проверка восстановления и данных; наличие файла не подтверждает пригодность копии |
| Контейнер работает от non-root | Это ограничение процесса; оно не равнозначно rootless Engine |
